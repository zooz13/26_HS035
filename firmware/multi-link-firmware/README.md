# ESP32-S3 CSI 순환 송수신 펌웨어

[`new-firmware`](https://github.com/team-ige-wae-andwae/new-firmware)는 향후 **A → B → C → D 순서로 한 대씩 송신하고 나머지 세 대가 수신하는 `RR4` 실험**에 사용할 펌웨어입니다. 네 보드 사이의 물리 링크 6개, 방향을 구분한 관측 12개를 수집합니다. ESP-IDF **6.0.1**, ESP32-S3 기준이며, 소스·배포 이미지·설치 스크립트·펌웨어 테스트만 포함합니다. 수집기 구현은 다른 담당자가 준비합니다.

현재 진행하는 고정 TX/RX의 1TX·3RX 및 1TX·4RX 실험은 **[기존 고정 TX/RX 펌웨어](https://github.com/team-ige-wae-andwae/firmware)**를 사용합니다. 현재 보드는 그 상태로 유지하고, 나중에 순환 실험을 시작할 때 이 이미지를 설치합니다. 이 저장소에는 `1X4` 모드나 E 노드가 없습니다. 다른 Codex에는 [한국어 인계서](HANDOFF_KO.md)를 전달하세요.

| 모드 | 필요한 보드 | 센싱 TX | 센싱 RX |
| --- | --- | --- | --- |
| `RR4` | A–D, 4개 | A → B → C → D | 해당 송신자를 제외한 3대 |
| `1X3` | A–D, 4개 | A | B, C, D |
| `2X2` | A–D, 4개 | A/B ↔ C/D | C/D ↔ A/B |

새 보드의 기본 모드는 `RR4`, 설정은 **노드당 송신 20 Hz / 순환 주기 50 ms**입니다. 명목 슬롯은 12.5 ms이며 전체 DATA 송신은 초당 80개입니다. 각 RX는 다른 세 TX에서 합계 초당 60개의 CSI를 목표로 받습니다. 네 보드 합계는 240개/초, 각 방향 링크는 20개/초입니다. 전파 간섭·송신 지연·패킷 누락으로 실제 값은 낮아질 수 있습니다.

역할은 패킷마다 바뀌지만 Wi-Fi를 매번 재시작하지 않습니다. 기존 `2X2`의 5초 그룹 교대와 `RR4`의 50 ms 순환은 서로 다른 스케줄입니다. RR4도 세 수신 슬롯이 12.5 ms 간격으로 이어지므로, 평균 수신률 60 Hz를 순간 간격까지 항상 일정하다는 의미로 해석하면 안 됩니다.

## 빌드 없이 설치하기

모든 보드에 같은 `prebuilt/` 이미지를 사용합니다. **Python과 esptool 5.x만 있으면 설치할 수 있으며, ESP-IDF 전체 빌드는 필요하지 않습니다.** ESP-IDF 6.0.1에 포함된 Python/esptool도 사용할 수 있습니다.

저장소 루트의 PowerShell에서, 포트 이름을 실제 연결된 보드에 맞춰 실행합니다. 다른 시리얼 모니터는 먼저 닫습니다.

```powershell
# Python 환경에 esptool이 없다면 최초 한 번만 설치
python -m pip install 'esptool>=5,<6'

# 장치 연결 없이 체크섬/설치 명령부터 검사
.\scripts\flash.ps1 -Port COM3 -DryRun

# 순환 실험을 시작할 준비가 되었을 때 설치
.\scripts\flash.ps1 -Port COM3

# ESP-IDF에 포함된 Python을 직접 지정하는 예시
.\scripts\flash.ps1 -Port COM3 -Python 'C:\Espressif\python_env\idf6.0_py3.12_env\Scripts\python.exe'

```

기본 플래시 속도는 **460800 baud**입니다. 통신 오류가 있을 때만 `-Baud 115200`으로 재시도합니다. 실행 정책이 스크립트를 막으면, 세 바이너리의 SHA-256을 `SHA256SUMS`와 대조한 뒤 `prebuilt/`에서 아래 명령으로 같은 이미지를 설치할 수 있습니다. 직접 esptool 명령은 체크섬을 자동 검사하지 않습니다.

```powershell
cd prebuilt
python -m esptool --chip esp32s3 -p COM3 -b 460800 write-flash "@flash_args"
```

이 명령은 부트로더 `0x0`, 파티션 테이블 `0xa000`, 앱 `0x20000`을 기록합니다. 이미지의 플래시 설정은 DIO/80 MHz/2 MB이고, 검증했던 보드는 물리 플래시가 8 MB인 ESP32-S3입니다. 보드의 메모리 전체를 지우지는 않습니다. 기존 팀 펌웨어와 같은 레이아웃이면 NVS(`0xb000`, 길이 `0x6000`)를 보존합니다. 다른 레이아웃/용도로 쓰던 보드는 기존 데이터를 백업한 뒤 설치하세요.

## RR4 설정과 시작

설치 후 콘솔은 **921600 baud, 8N1**입니다. 아래 명령은 줄바꿈(LF)으로 끝내며, 각 행을 해당 보드에만 전송합니다. 보드마다 ID가 달라야 합니다.

```text
NODE CONFIG A RR4 20 50
NODE CONFIG B RR4 20 50
NODE CONFIG C RR4 20 50
NODE CONFIG D RR4 20 50
```

각 보드에서 `NODE STATUS`로 서로 다른 ID, `RR4`, `20`, `50`, `STOPPED`를 확인합니다. `CONFIG`는 설정을 저장하고 해당 보드를 정지시킵니다. 이전 `csi_node_v2` 설정이 NVS에 있으면 새 기본값보다 우선하므로, 새 이미지를 설치한 뒤에도 **네 보드 모두 CONFIG**합니다.

B/C/D에 `NODE START 1001`을 먼저 보내고, **A에 마지막으로 같은 명령**을 보내면 시작합니다. 새 실험마다 새로운 공통 session 번호(1–4294967295)를 사용합니다. `NODE STOP`은 명령을 받은 보드만 정지시키므로, A부터 정지한 뒤 나머지 보드도 정지합니다.

전원을 다시 켜면 저장된 설정을 유지하면서 **항상 STOPPED로 부팅**합니다. 플래시 설치만으로 실험이 자동 시작되지 않습니다.

RR4는 `(노드당 Hz, 순환 ms)` 조합으로 `(5, 200)`, `(8, 125)`, `(10, 100)`, `(20, 50)`을 지원합니다. 기본 20 Hz가 상한입니다. 기존 송수신 보호 간격을 유지하므로 `40 25`나 1 ms·0.5 ms 순환은 지원하지 않습니다.

## 기존 비교 모드

새 바이너리에서도 기존 명령을 유지합니다. 진단용 `1X3`는 각 보드에서 `NODE CONFIG <ID> 1X3 40 5000`으로 설정하며, A만 송신하고 B/C/D가 수신합니다. 이 모드는 기존 고정 RX 펌웨어나 기존 수집기와 같은 출력 형식이라는 뜻은 아닙니다.

## 역할이 교대하는 2X2 설정

기존 방식과 비교할 때는 A–D 네 보드의 모드를 `2X2`로 설정합니다. B/C/D부터 동일한 session으로 START한 뒤 A를 START합니다. A/B가 센싱 TX이고 C/D가 RX인 구간과, C/D가 TX이고 A/B가 RX인 구간을 번갈아 실행합니다. 역할 교대는 재플래시 없이 같은 펌웨어 안에서 진행합니다.

```text
NODE CONFIG A 2X2 40 5000
NODE CONFIG B 2X2 40 5000
NODE CONFIG C 2X2 40 5000
NODE CONFIG D 2X2 40 5000
```

## 수집기 담당자에게 전달할 규약

[펌웨어 프로토콜 문서](csi_node/README.md)에 UART 명령/응답, 상태와 타이밍 카운터, CSI CSV v2 형식을 정의했습니다. `RR4`의 `phase`는 4슬롯 순환 번호(`slot / 4`)이며, `seq`는 전역 슬롯이라 같은 TX에서는 4씩 증가합니다. 이 정상 간격을 누락으로 계산하면 안 됩니다. 링크와 관측은 `session + tx_id + rx_id + slot`으로 구분합니다.

`csi_b64`를 디코딩한 길이가 `csi_len`과 같은지 확인한 뒤 signed int8로 복원합니다. 길이는 **1–768바이트의 가변값**이며 384로 고정하지 않습니다. 원본과 PHY 메타데이터를 보존하고, 서로 다른 길이를 조용히 버리거나 패딩하여 섞지 않습니다. `first_word_invalid=1`이면 첫 4바이트를 유효한 측정값으로 사용하지 않습니다. 큐와 base64 출력은 UART 처리 부담을 줄이지만 무선 손실을 없애지는 않습니다.

`NODE STATUS`의 추가 진단행 `NODE_CSI_STATS,min_len,max_len,invalid_length_dropped`는 해당 세션의 CSI 길이 범위와 잘못된 길이/버퍼의 폐기 횟수를 보여줍니다. 기존 `NODE_STATUS` 필드는 유지합니다. 기존 Gateway의 384 I/Q 값·192 amplitude 고정 처리는 별도 수집/분석 제약이므로, 새 가변 길이 출력을 그대로 연결하기 전에 담당자가 검토해야 합니다.

CSI 길이 변화가 과거 누락의 원인이었다고 확인된 것은 아닙니다. 확인한 2026-10-08 저장 자료는 모두 384바이트였고, 기존 RX의 Wi-Fi 콜백 안에서 긴 정수열을 출력하며 대기하는 처리가 병목 가능성이었습니다. 큐·base64는 이 부담을 완화하는 변경이며 현재 고정 TX/RX 보드에는 아직 설치하지 않았습니다.

## 소스 수정 후 빌드

ESP-IDF **6.0.1** PowerShell 환경에서 저장소 루트 기준:

```powershell
.\scripts\build.ps1
```

스크립트는 `%TEMP%\ige-csi-node-idf601`의 영문 경로에 소스를 복사하고 빌드 캐시를 재사용합니다. 최초에만 target을 지정하며, 성공하면 `prebuilt/`의 이미지와 체크섬/소스 해시를 갱신합니다. 임시 경로에 한글이 포함되면 `-StageDirectory C:\temp\ige-csi-node`처럼 지정합니다. 이 디렉터리는 이 프로젝트 전용으로 사용하세요. 설정 변경 시 기존 `sdkconfig` 값이 우선하므로 새 staging 디렉터리를 지정해 빌드하세요.

일반 ESP-IDF CLI도 지원합니다. 영문 경로에서 최초 한 번 `idf.py set-target esp32s3`, 이후 `idf.py build`를 실행합니다. 동일 버전을 여러 보드에 설치할 때는 빌드를 한 번만 하고 `flash.ps1`을 포트별로 실행하면 됩니다.

```powershell
python -m pytest tests/test_node_protocol.py -q
```

위 테스트는 PC용 C 컴파일러(GCC/Clang/MSVC)로 실제 프로토콜 헤더를 컴파일하여 실행합니다. 필요하면 `CSI_HOST_CC`에 컴파일러 경로를 지정합니다.

## 검증 범위

- 2026-10-14 네이티브 C 프로토콜 테스트(`1 passed`), ESP-IDF 6.0.1 빌드, 버전 3.0.0 이미지·체크섬·설치 dry-run 검사를 통과했습니다. **새 RR4 버전은 실기기에 설치하거나 네 보드로 수집하지 않았습니다.** 실제 RR4 수신률·손실률은 별도 실측이 필요합니다.
- 선행 `1X3`/`2X2` 버전은 2026-10-14 A/C 두 보드로 단방향 수신, 양방향 교대, 정지와 재부팅 정지 상태를 실측했습니다. 그 최종 테스트의 잘못된 CSI 행/CSI 큐 넘침/송신 오류/FAULT는 0이었습니다. **이전 이미지의 결과를 새 RR4 이미지의 실측 결과로 사용하지 않습니다.**
- 이전 두 보드 2X2 실측의 스케줄 주파수는 활성 TX당 약 39.05–39.09 Hz, 수신 기록 주파수는 35.75–37.09 Hz였습니다. 전체 네 보드의 교대·순환 실험과 장시간 검증은 별도로 필요합니다.

기존 TX가 60 Hz였던 원인은 예전 펌웨어의 NVS `csi_ctrl/rate_hz=60`이 소스 기본값 40을 덮어쓴 것이었습니다. 이 펌웨어는 별도 `csi_node_v2` 설정을 쓰므로 이전 60 Hz 값을 가져오지 않습니다.
